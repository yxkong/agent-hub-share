# 提取契约

## 输入材料类型

| 类型 | 常见来源 | 重点 |
|---|---|---|
| 会话 | AI 编程会话、需求讨论、历史 session | 决策变化、约束、取舍、失败修正 |
| 调试 | 日志、错误栈、排查过程 | 根因、定位方法、验证闭环 |
| 重构 | diff、设计文档、迁移清单 | 架构问题、边界收敛、收益 |
| 优化 | 性能、准确率、成本、稳定性 | 指标前后对比、测试方法 |
| 治理 | 编码、脚本、技能、规范 | **仅**消费者碰撞、静默漂移、封装泄漏等运行时/语义问题；放置表 alone → skill_rule |
| 表达 | 面试稿、简历草稿、文章草稿 | 事实还原、亮点合并、可信表达 |
| 设计文档 | 架构设计、方案设计、TODO、评审文档 | 设计取舍、能力边界、风险控制 |
| 指定代码 | 代码文件、类、方法、模块目录 | 抽象设计、扩展性、可观测性、工程质量 |

## 字段模型

每个有效经验点必须尽量补齐：

| 字段 | 说明 |
|---|---|
| canonical_id | 唯一知识点 ID，入库前按去重规则生成 |
| asset_type | 资产类型，如 case、principle、anti_pattern、interview_story |
| problem | 遇到的真实问题，不写泛泛目标 |
| root_cause | 根因或关键约束，缺证据时标 assumption |
| decision | 为什么选择该方案，放弃了什么 |
| solution | 落地动作、技术机制、关键链路 |
| validation | 如何验证有效，含命令、指标、页面或日志证据 |
| impact | 量化收益或未量化收益，禁止编造 |
| principle | 可迁移的方法论 |
| tags | 场景、技术、能力标签 |
| evidence | 输入中的依据摘要 |
| source_anchor | 会话轮次、文档章节、代码路径、方法名、diff 片段或日志片段 |
| architect_view | 架构师快测结论：`strong` / `weak` / `policy_only`；`policy_only` → 不进 Vault |
| vault_admit | `yes` / `merge_only` / `no`；`no` 时写明转交目标（skill-engineering / doc-script / prompt-engineering） |
| depth_level | L1–L4（见 `value_lens.md`）；L1 或纯 policy 的 L2 → 默认 `vault_admit: no` |
| score_vault_worthy | 1–10（见 `value_lens.md` §双轴评分） |
| score_expressibility | 1–10（见 `value_lens.md` §双轴评分） |

## 治理类会话约束

- 主交付均为治理文档时：**最多 1 张** canonical（优先 `decision_model`）。
- 脚本 L1/L2 放置契约：写入 skill references，**不**单独建 `case` canonical。
- StrictMode / 薄封装类问题：作为脚注并入已有决策卡或 loader 碰撞卡。

## 证据规则

- 输入明确出现的数据、命令、日志、diff、验收结果，标为 `fact`。
- 根据上下文合理推断但无直接证据，标为 `assumption`。
- 关键字段缺失时写 `unknown`，并给出最小补证建议。
- 收益只允许来自事实；没有事实时写"未量化收益"。
- 会话中如果出现多轮修正，以最后被验证的结论为准，旧结论进入 evidence 或 discarded_notes。

## 输入范围隔离

用户粘贴了片段、交付清单或指定文件时，默认只从该范围提取。

禁止：
- 把当前会话里其他历史问题混入输出。
- 用旧上下文补充不在片段中的技术事实。
- 因为记得某个项目背景，就把片段外的 bug 修复写成资产。

允许：
- 从片段内事实做直接语义聚合，例如把"评测接口 + 分项分数 + trace + dashboard"聚合为"RAG 可观测性体系"。
- 标注片段内未给出的收益为 `assumption` 或 `unknown`。

## 从设计文档 / 代码提炼亮点

设计文档和指定代码不是只找问题，也要识别做得好的设计：

- 设计文档：重点看目标是否清晰、边界是否收敛、方案取舍是否合理、风险和验收是否完整。
- 指定代码：重点看抽象是否稳定、扩展点是否清晰、错误处理是否闭环、可观测性和测试入口是否足够。
- diff：重点看从旧实现到新实现，系统能力是否提升，而不是只列改了哪些文件。

输出时必须给出源锚点，例如文档章节、代码路径、类/方法名或 diff 摘要。

## 三维价值评估（每个候选必须通过）

提炼前问：**这条资产在以下三个维度中，有至少一个维度的实质贡献吗？**

| 维度 | 判断标准 | 典型正例 | 典型反例 |
|---|---|---|---|
| **技术能力** | 体现了能构建/设计/解决什么 | "设计了 RAG 可观测性体系：分项分数 + 链路追踪 + 健康 Dashboard" | "修复了软删除字段缺失" |
| **个人成长** | 对某类问题有了新的认知框架 | "RAG 链路 HTTP 200 不等于功能生效，需要召回测试验证" | "字典 key 要和实体类型保持一致" |
| **业务价值** | 产品/用户/团队得到了实际改善 | "RAG 效果从不可量化到可量化：引入评测接口 + 健康 Dashboard" | "命名规范统一了" |

三个维度全部为"反例"特征 → 丢弃，不要只是为了把卡片填满。

强制门禁：

```text
如果候选资产的价值只能表述为"遵守规则 / 修掉违规 / 字段补齐 / 命名统一"，则不是技术资产。
只有当它能上升为能力建设、业务价值或个人成长时，才进入输出。
```

## 能力类 vs 修复类 分类

| 类别 | 定义 | 处理 |
|---|---|---|
| **能力建设** | 之前没有、现在有了的技术能力/产品能力 | 必须提炼，用能力视角描述 |
| **架构洞察** | 对系统设计、技术机制的非显而易见理解 | 提炼，说清楚"为什么非显而易见" |
| **bug fix（规范违反）** | 规则/规范被违反后的修复 | 丢弃；只体现知道规范，不体现技术深度 |
| **规范补全** | 命名约定、字段约定、编码规范的补充 | 丢弃；这是表格任务，不是洞察 |

## 从交付清单提炼的聚合规则

交付清单通常不是逐项提炼，而是聚合成 2-4 个能力资产。

优先合并：
- 同一目标下的多个 GAP，例如评测接口、分项分数、trace、dashboard 合并为"RAG 可观测性与评测体系"。
- 同一质量链路下的多个修复，例如 minSimilarityScore、ReRank、严格模式、兜底提示合并为"RAG 质量门控体系"。
- 同一用户信任链路下的多个功能，例如引用深链、chunk 高亮、失败原因展示合并为"可解释与可追溯体验"。

不要逐项输出：
- 单个字段透传
- 单个按钮封装
- 单个异常 catch
- 单个 mapper/DTO 补字段

## 抽象层次校准（每个候选必须校准）

**太泛**（"做了一次产品能力 GAP 分析"）→ 必须具体化到最核心的 1-2 个洞察，说清楚：
- 这类问题的识别方式是什么
- 哪个决策最有价值，为什么
- 洞察可以推广到哪类场景

**太具体**（"这次 agent 按文件所有权拆分任务"）→ 必须抽象到可迁移原则，说清楚：
- 这个原则适用的通用场景
- 背后的约束是什么（不是"我们这次怎么做的"）

## 过滤规则

丢弃：
- 纯流水账："先做了 A，又做了 B，最后成功了"
- 无结果的猜测
- 与技术能力无关的情绪或沟通细节
- 不能脱敏的私有信息
- 纯规则复述（没有失败/踩坑背景支撑的编码规范、命名约定）
- AI 执行过程描述（"agent 分 3 轮并行"是执行方式，不是洞察）

优先保留：
- **能力建设**：构建了之前不存在的技术/产品能力层（评测、可观测、质量门控等）
- **系统性解决方案**：不是修一个 bug，而是设计了一类问题的解法体系
- **非显而易见的根因**：表面现象 A，真实原因是 B 层的 C 机制（读者意想不到）
- **有取舍的决策**：选了 A 方案，明确说明放弃了 B/C，以及为什么
- **复杂问题定位方法**：如何从现象缩小到根因的推理链路（推理过程本身有价值）
- **可量化或可验证的改进**：性能、准确率、可观测性，有前后对比或测试证据

丢弃（以下内容一律不提炼为优化点卡片）：
- 命名规范/字段命名/软删除约定的补全 → 应该做的基础工作
- 纯 bug 修复（规范违反）→ 没有技术深度增量
- AI agent 执行方式、轮次分配 → 不是个人技术能力
- 会话中的尝试过程 → 只保留被验证的最终结论

## 默认一句话输入

用户不需要指定类型。以下一句话足够触发完整抽取：

```text
请从当前会话提炼 TechInsightVault 技术资产。
```

执行时默认完成：

- 自动识别资产类型
- 自动去重和合并同义知识点
- 自动给出归档路径
- 自动标注缺失证据
