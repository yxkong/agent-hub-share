# RAG 交付清单提炼示例（可选领域样例）

本文件只是 RAG 领域样例，不是默认必读项，也不代表本技能只服务 RAG。

默认多领域样例见 `domain_examples.md`。

## 输入特征

输入是一组 RAG GAP 交付项，例如：

- minSimilarityScore 生效
- ReRank 自动生效
- 分项分数 DTO
- 引用深链
- 评测接口前端
- 健康 Dashboard
- 纯 RAG 模式
- 多库 UI 多选
- RAG 链路追踪

不要逐项输出 9 张卡片。应聚合为 3-5 个能力资产。

## 正确提炼方式

主表达不要出现 G07/G14/G12。先讲读者能理解的系统问题，再讲解决方案和效果；内部编号只放证据附录。

### 资产 1：RAG 评测与可观测性体系

- 原系统问题：用户只能看到最终回答，无法判断 RAG 效果好坏；一旦回答不准，也不知道是召回、关键词匹配、重排还是文档状态出了问题。
- 解决方案：建立评测入口、分项分数、链路追踪和健康面板，把召回质量、耗时、文档状态和错误原因显性化。
- 带来的效果：RAG 从黑盒问答变成可度量、可诊断、可运营的系统；效果问题可以被复现、定位和持续跟踪。
- 体现能力：AI 系统工程能力、可观测性体系设计能力、平台化治理能力。
- 证据附录：分项分数 DTO、评测接口、健康 Dashboard、RAG 链路追踪。

### 资产 2：RAG 召回质量门控体系

- 原系统问题：检索结果只要返回了内容就可能进入大模型上下文，低相关片段、未重排结果、无命中场景都会让回答质量不可控。
- 解决方案：在进入 LLM 前建立质量门控：相似度阈值过滤、重排、无命中兜底和严格模式组合生效。
- 带来的效果：低质量内容更难进入上下文，无依据时能明确拒答或提示，降低幻觉风险。
- 体现能力：RAG 质量治理能力、生成前控制链路设计能力。
- 证据附录：minSimilarityScore、ReRank 自动生效、置信度兜底、纯 RAG 模式。

### 资产 3：RAG 答案可信引用与可解释体验

- 原系统问题：AI 给出答案后，用户难以核验答案来自哪篇文档、哪一页、哪一个片段。
- 解决方案：打通答案、引用、原文 chunk 和页码定位，让用户能从回答跳回证据位置。
- 带来的效果：答案来源可追溯，用户可以审计和核验回答，降低知识库问答的信任成本。
- 体现能力：可信 AI 产品设计能力、证据链交互设计能力。
- 证据附录：引用深链、chunk 高亮、页码定位、召回表格。

### 资产 4：知识库运维健康闭环

- 原系统问题：文档上传和索引失败后，状态和原因不够清晰，容易出现一直 INDEXING 的僵尸文档，运营和研发都不知道问题卡在哪里。
- 解决方案：补齐失败状态、错误原因、健康面板和文档生命周期状态治理。
- 带来的效果：失败可见、原因可查、健康情况可汇总，知识库从"任务提交"升级为"可运营平台"。
- 体现能力：平台运维闭环设计能力、失败态治理能力。
- 证据附录：批量上传失败处理、失败原因展示、健康 Dashboard。

### 资产 5：多知识库与多向量后端扩展架构

- 覆盖项：向量库路由、多库 UI 多选、向后兼容 ragLibId/ragLibIds。
- 技术能力：将单知识库、单向量后端能力抽象成可扩展平台能力。
- 业务价值：支持多知识库组合问答和不同向量库后端演进，降低后续扩展成本。
- 个人成长：平台化设计要在参数契约、路由策略和兼容迁移上一起考虑。
- 方法论：AI 平台能力扩展不能只改 UI，多选输入、后端路由、旧参数兼容必须形成一条完整契约链。

## 不应输出

不要把以下内容作为主卡片：

- "字段 docId 未透传"
- "enableLlmScoring 门控写错"
- "catch 块没标失败"
- "tooltip 没展示 errorMsg"
- "ORM 父类字段隐式捕获"

这些是实现缺口或工程规范问题。它们只有聚合到能力体系里，才有面试和简历价值；ORM/SQL 规范违规类问题默认不入能力资产。
