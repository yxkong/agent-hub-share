# 会话抽取策略

目标：从 Cursor / Claude / Codex 等 AI 编程会话中提炼**能力、价值、成长**三类资产。

会话中的规则、规范、普通 bug 多数只说明 AI 没有遵守用户规则，不是用户能力资产。

---

## 发现阶段：先扫高价值信号（发现优先于过滤）

**在做任何过滤之前，先扫描会话中的高价值信号**。这一步的目的是"找到值得放大的 20%"，而不是"排除不该要的 80%"。

| 信号类型 | 识别方式 | 资产潜力 | 深度层级 |
|---|---|---|---|
| **新系统能力**：之前没有、现在有了 | 功能交付清单、GAP 分析、新模块 | 聚合为能力体系 | L2–L3 |
| **架构决策 + 放弃选项**：面对多个方案做了明确取舍 | "我们选了 A 放弃了 B，原因是…" | 决策模型、方法论 | L3–L4 |
| **非显而易见的根因**：角色测试：架构师会觉得这个根因不 trivial | 报错后的根因分析，不是"忘了加字段" | debug 洞察 | L2–L3 |
| **认知升级**：之前的理解被打破，建立新框架 | "我之前以为 X，实际上是 Y…" | 成长资产、面试故事 | L4 |

**高价值信号的反面（直接跳过，不用分析）**：
- AI 执行方式（"分了几轮 agent"、"先改哪个文件"）
- 规则/规范补全（字段命名、软删除规范）
- AI 没遵守规则后的修复
- **主交付为治理文档**：SKILL/references/放置表/script_tiering/backup SOP（→ Deliverable Gate，见 `value_lens.md`）
- **Hub 脚本 L1/L2 分级表 alone**（正文已在 skill references，不进 Vault）

**治理类会话**：主交付均为治理文档时，全会话 **最多 1 张** TechInsightVault canonical（优先 `decision_model`）；其余转 skill-engineering / doc-script-governance 或 `discarded_notes`。

---

## 提炼视角优先级

提炼时始终从最高价值视角向下看，不要从"发生了什么"向上总结：

1. **能力视角（最高优先）**：这次会话构建或展示了什么技术能力？
   - 例：设计了 RAG 质量监控体系、实现了召回可观测性、构建了评测闭环
2. **成长视角**：遇到了什么认知挑战，解法让你对某类问题有了更深的理解？
   - 例：发现 RAG 链路上 HTTP 200 不等于功能生效
3. **业务价值视角**：这次工作让产品/团队/用户得到了什么？
   - 例：RAG 效果从"不可量化"到"可量化可监控"

**不主动提炼的**：普通 bug 修复、规则/规范补全、AI 违反用户规则后的返工。

## 默认范围

用户未指定内容时，不要求用户先挑片段；按 `session_history_sources.md` 从可访问会话历史中发现候选。

用户指定工具或时间范围时，以指定范围为准：

- Cursor / Claude / Codex
- 当前会话 / 最近 N 次会话 / 某项目历史会话
- 用户粘贴的局部片段

## 快速扫描

### 第一步：先扫"交付物/构建了什么"（高价值信号）

会话中出现以下内容时，**优先**从能力/价值视角提炼：

| 信号 | 要问的问题 |
|---|---|
| 功能交付列表（GAP 清单、checklist） | 哪些能力是之前没有的？这些能力组合起来解决了什么核心问题？ |
| 新模块/新组件/新接口 | 这个能力层在系统中扮演什么角色？为什么这个设计决策有价值？ |
| 性能/质量/可观测性改进 | 指标变化说明什么？可观测/可测试本身有什么价值？ |
| 架构决策和取舍 | 为什么这个方向，放弃了什么，背后的约束是什么？ |

### 第二步：再扫"非显而易见的问题"（中价值信号）

| 信号 | 抽取价值 | 注意 |
|---|---|---|
| 报错与日志 | 根因推理链路（只有根因非显而易见时才保留） | 根因"就是忘了加某字段"→ 丢弃；根因"是架构层的隐式冲突"→ 保留 |
| 方案取舍 | 为什么选这个，放弃了什么 | **必须包含放弃原因**，否则不是决策洞察 |
| 反复追问 | 认知难点的所在 | 追问多次说明认知难度高，值得沉淀 |
| 用户纠正方向 | 真实约束背后的原因 | 只保留"为什么会错"，不是"改成了什么" |

> **关键难点识别**（内部可称"硬点"）：以下问题任一为 YES，说明有面试价值：
> - 普通工程师看了代码/日志，会往错误方向定位吗？
> - 解决方案需要理解某个架构层的隐式约束吗？
> - 如果不做这件事，问题会静默存在而不报错吗？

**不抽取为能力资产**：
- AI 执行方式（"分了几轮、几个 agent、哪些文件"）
- 规则/规范补全（命名约定、字段命名、软删除规范）
- 纯 bug 修复（尤其是 AI 未遵守既定规则导致的修复）
- 会话中的尝试过程（保留最终结论，过程进 discarded_notes）

这些内容可转入：

- `discarded_notes`：说明为什么不入 Vault
- `rule_improvement_candidates`：用于改进 rules / skill / checklist
- 不进入面试表达、简历 bullet、能力资产卡

## 两遍抽取

**默认模式（单次输出）**：两遍合并后直接输出完整结果。
**分步确认模式**：用户明确说"先给候选列表"或"先看看有哪些"时，第一遍只输出摘要列表，等用户确认后再生成完整卡片。

第一遍：广覆盖，抓候选片段。

- 每个候选只记一句话摘要
- 记录来源位置或上下文锚点（如"会话第 N 轮""用户纠正 X"）
- 不急着写面试表达

第二遍：高价值筛选 + 三维价值测试。

- 合并同义候选
- 删除没有决策、没有验证、没有迁移价值的片段
- 把剩余候选映射为资产类型
- **三维价值测试**（每个候选必须在至少一维得分）：
  - 技术能力：体现了能解决什么复杂问题/能构建什么系统
  - 个人成长：让开发者对某类问题有了更深理解
  - 业务价值：让产品/用户/团队得到了实际改善
- **角色视角测试**：架构师看了这条会说"这人懂 XXX"还是"这不就是基础操作"？后者 → `architect_view: policy_only`，`vault_admit: no`
- **Deliverable Gate**：主交付为 skill/doc 正文时，不进入第二遍 Vault 筛选，直接转交表

流水账识别（以下任意一条成立即为流水账，降级或丢弃）：
- 描述的是"做了什么步骤"而不是"为什么这样做、不这样做有什么后果"
- 把 AI 的执行分工当成洞察输出
- 核心内容只是确认了一条已有规范的正确性
- **核心是"修了一个规范违反"**：表明知道规范，但不表明有技术深度
- **核心是"AI 没按规则做"**：表明工具协作失败，不表明个人能力

## 长会话处理

**长会话判断阈值**：对话轮次 ≥ 15 轮 或 总字符数 ≥ 8000，按以下阶段切块；否则不分块，直接整体两遍抽取。

长会话按阶段切块：

1. 需求与约束
2. 设计与决策
3. 实现与变更
4. 失败与修正
5. 验证与结果
6. 可复用原则

每块最多提炼 3 个候选，最后全局去重。

## 输出原则

- 优先输出少量高质量资产，不追求覆盖每一句。
- 对没有验证的洞察，写成待补证候选。
- 对重复出现的知识点，合并为一个 canonical asset。
