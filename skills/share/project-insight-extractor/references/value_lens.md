# 价值视角门禁

目标：防止把规则违规、字段补齐、普通 bug、AI 未遵守规则导致的返工包装成"技术资产"；并防止**治理文档落盘**被误归档为 TechInsightVault 案例。

## 主交付物门禁（Deliverable Gate，SOP 第 3.5 步）

**先看会话主交付物是什么**，再决定是否进入 Vault。主交付物指：本轮对话最终落盘、用户验收的对象（文件/脚本/SKILL/references），不是讨论过程。

| 主交付物 | 去向 | Vault |
|---|---|---|
| `SKILL.md` / `references/*.md` 正文 | `skill-engineering` | ❌ |
| 放置表、路由表、script_tiering、backup 规范 | `doc-script-governance` / 对应 skill references | ❌ |
| `*.prompt.md` 长指令 | `prompt-engineering` | ❌ |
| `rules/common` / `PROJECT_RULES` / `AGENTS.md` 规则正文 | `skill-engineering` + sync 脚本 | ❌（决策模型可单独提炼，见下） |
| 运行时 bug / 能力构建 / 架构取舍 | 本技能 | ✅ 按后续门禁 |

**硬规则**：若价值只能表述为「写清了 L1/L2 放哪 / 文档放哪 / 路由表 / 备份 SOP」，归类为 `skill_rule` 或 `governance_policy`，**终止 Vault 路径**，最多输出 `rule_improvement_candidates` 或转交表。

**例外（可进 Vault）**：同会话中除治理文档外，还有**消费者侧碰撞**（loader 误扫 `.bak` 当 skill）、**静默语义漂移**（同名 L1–L4 两套评分）、**运行时封装泄漏**（StrictMode 导致子脚本假未赋值）等——须写清「谁在读、误读后果、如何验证」，不能只复述分级表。

## engineering_governance 域准入

| 主题 | Vault | 说明 |
|---|---|---|
| COMMON/PROJECT 分层、合并后重复指令 | ✅ `decision_model` | 消费者是 Agent；有拼接前后对比 |
| skill loader / 索引误扫归档目录 | ✅ `case` / `anti_pattern` | 运行时行为或静默错误 |
| 同名标签两套语义（如 L1–L4） | ✅ `anti_pattern` | 碰撞 + 重命名 + 验证 |
| Hub 脚本 L1/L2 **放置契约** alone | ❌ → skill references | 正文已在 `script_tiering.md` |
| backup 薄封装 + StrictMode 泄漏 | ⚠️ 脚注 | 并入规则分层或 loader 卡，**不**单独 canonical |
| 文档 backup 三步 SOP | ❌ → doc-script | 流程文档，非洞察 |

**治理类会话上限**：整段会话若主交付均为治理文档，TechInsightVault **最多 1 张** canonical（优先 `decision_model`）；其余进 skill/doc-script，或 `discarded_notes`。

## 三问门禁

每个候选必须至少回答其中一问：

1. **技术能力**：它体现我能设计、构建或治理什么系统能力？
2. **个人成长**：它让我形成了什么新的判断框架或架构认知？
3. **业务价值**：它让用户、业务、团队或平台获得什么可感知改善？

如果只能回答"我修了一个不该错的问题"或"AI 没按我的规则做，我纠正了它"，丢弃。

## 规则违规过滤

以下内容默认不是能力资产：

| 内容 | 为什么丢弃 |
|---|---|
| 字段未透传 | 基础实现完整性，不是洞察 |
| 命名/类型/字典不一致 | 规则违反，不是能力 |
| 软删除缺失 | 基础数据规范，不是能力 |
| ORM 父类字段隐式捕获 | 遵循 SQL/实体字段语义规范即可避免，不是能力 |
| SQL/DDL 与实体语义不一致 | 工程规范违反，不是能力 |
| 普通 bug | 修错不等于能力资产 |
| AI 未按规则执行 | 工具协作失败，不是个人技术亮点 |
| 单个按钮或 tooltip | 产品细节，不是体系 |
| 单个 catch 或状态修复 | 兜底缺失，不是体系 |

保留条件：

- 多个单点共同构成一套能力，例如"失败状态 + 错误原因 + 健康面板 + 僵尸任务清理"可以聚合为"知识库运维健康闭环"。
- 能明确说明业务价值，例如"失败可恢复、问题可定位、减少不可见失败"。

## AI 执行噪音处理

从 AI 编程会话历史抽取时，必须先识别 AI 执行噪音：

| 噪音 | 去向 |
|---|---|
| AI 没遵守已存在规则 | discarded_notes |
| 用户反复提醒同一规则 | rule_improvement_candidates |
| AI 修复自己造成的 bug | discarded_notes |
| 批量改造未 sample-first | rule_improvement_candidates |

只有当这些噪音沉淀成更高层能力时才保留，例如：

- "建立 sample-first codemod 验证门禁，降低批量改造返工风险"
- "将 AI 协作规则沉淀为可执行 skill/checklist，提高交付一致性"

注意：这类保留项表达的是**AI 协作治理能力**，不是具体 bug 修复。

## 工程规范问题硬过滤

如果一个候选的根因可以归结为"没有遵循既有 SQL 规范、实体设计规范、字段命名规范、软删除规范、字典规范"，则默认不进入 TechInsightVault。

典型丢弃：

- ORM 父类 `status` 字段捕获子类业务状态列。
- DB 字段类型和 Java 实体类型不一致。
- 字典 key 和前端枚举值不一致。
- 软删除字段未映射。

保留条件只有一个：会话中真的构建了防止此类问题复发的**体系能力**，例如 schema lint、DDL-Entity 一致性检查、迁移验收工具。此时资产标题必须写体系能力，而不是写具体 bug。

## 架构师视角

从架构师视角，优先提炼：

- 系统从黑盒到白盒：可观测、可追踪、可解释。
- 系统从功能可用到效果可控：评测、质量门控、阈值、严格模式。
- 系统从单点功能到平台能力：多库、多向量后端、兼容演进。
- 系统从人工排查到运营闭环：健康面板、失败原因、状态治理。

## 业务价值表达

不要写：

```text
修复 ReRank 开关不生效。
```

要写：

```text
建立 RAG 召回质量门控，让排序、阈值过滤和严格模式真正参与回答生成，降低低相关 chunk 进入上下文导致的幻觉风险。
```

不要写：

```text
增加分项分数 DTO。
```

要写：

```text
把召回结果拆成 vector/keyword/rerank 分项分数，使 RAG 效果问题可以定位到检索、关键词匹配或重排阶段。
```

## 个人成长表达

从"我修了什么"转成"我形成了什么判断"：

- RAG 系统不能只验接口成功，要验回答质量、召回证据和链路分数。
- AI 产品的可信度来自可解释引用、可观测链路和失败兜底，而不是单次回答看起来正确。
- 平台型 AI 能力要把评测、可观测、运维闭环前置为基础设施，而不是上线后的排障工具。

## 资产深度分级（L1–L4）

通过价值门禁的内容还需要判断深度层级。**只有 L3/L4 适合面试表达和简历 bullet**；L2 进案例库；L1 不入 Vault。

| 级别 | 特征 | 典型表现 | 表达策略 |
|---|---|---|---|
| **L1：做了什么** | 功能列表、步骤记录、实现了某字段 | "增加了 X 字段" / "修复了 Y bug" | 丢弃；放 `00_inbox` 等待二次提炼 |
| **L2：设计了什么机制** | 抽象设计、接口定义、扩展点、**改变运行时行为**的错误闭环 | "设计了可插拔的向量库路由策略" | 写成案例卡；**纯 policy/放置表不算 L2**，属 `skill_rule` |
| **L3：形成了什么判断框架** | 面对选择时的判断原则，可复用于类似场景 | "RAG 可信度需要质量门控 + 引用溯源 + 运维闭环三要素" | 事实源目录由 `asset_type` 决定；可同步提炼面试表达 |
| **L4：改变了对某类问题的系统认知** | 原有认知被打破，建立新的思维模型 | "AI 产品上线不是终点，而是可持续度量的起点" | 同上；优先进面试/简历精选 |

**深度判断捷径**：
- 问自己："如果不做这件事，系统会有什么可感知的问题？" L1/L2 通常回答"功能缺失"，L3/L4 回答"某类问题永远无法被发现或解决"。
- 问自己："这条认知能指导我在下一个完全不同的项目里做出更好的决策吗？" 能 → L3/L4，不能 → L1/L2。

## 聚合与拆分标准

多个交付项提炼为资产时，按以下标准决定是聚合还是拆分：

**聚合条件（满足其一即可合并）**：
- 共享同一受益对象（同样的用户/运营/研发获益）
- 共享同一底层技术机制或设计思想
- 在面试中自然会讲成同一个故事

**拆分条件（满足其一则分开）**：
- 认知框架不同（如"效果可度量"和"失败可运营"是两种独立判断）
- 面试受众不同（技术深度 vs 产品影响力）
- 证据来源完全不重叠

**实操示例**（RAG 场景）：
- 分项分数 + trace + 评测入口 + 健康面板 → 聚合为"RAG 可观测性体系"（L3，共享"效果可度量"框架）
- minSimilarityScore + ReRank + 严格模式 + 无命中兜底 → 聚合为"RAG 召回质量门控"（L3，共享"质量前置控制"框架）
- 上面两组 → 拆分（一个是"可度量"，一个是"可控制"，是两套不同认知）

## 双轴评分（10 分制，卡片必填）

每张候选在落盘前打两分；**任一分 ≤3 且另一分 ≤5 → 丢弃或仅 `discarded_notes`**。

| 轴 | 问什么 | 8–10 | 4–7 | 1–3 |
|---|---|---|---|---|
| **vault_worthy** | 去掉会话上下文，这条仍值得单独存 Vault 吗？ | 决策/碰撞/认知升级，有验证 | 可合并进更大 canonical | 规则复述、放置表、SOP 副本 |
| **expressibility** | 面试/简历能讲出「为什么不显而易见」吗？ | L3–L4，有放弃方案与验证 | L2 机制故事 | L1 或纯文档维护 |

**architect_view 快测**（与 `expressibility` 对齐）：架构师读完会说「这人懂 XXX」→ ≥7；「这不就是写文档/守规范」→ vault_worthy ≤4，**不进 Vault**。

**与 asset_type 关系**：`skill_rule` / `governance_policy` 两轴均按 1–3 处理，直接转交，不写 TechInsightVault 路径。
