# 源锚点

目标：让技术资产有可追溯证据。源锚点不只来自会话历史，也可以来自设计文档、指定代码、diff、日志或用户粘贴片段。

## 支持的源锚点

| 来源 | 锚点写法 | 适合提炼什么 |
|---|---|---|
| 会话历史 | 工具名 + 会话范围 + 关键轮次摘要 | 决策变化、交付成果、用户纠偏后的方法论 |
| 设计文档 | 文档路径 + 章节标题 | 架构取舍、能力边界、验收设计、风险控制 |
| 指定代码 | 文件路径 + 类/方法/组件名 | 抽象设计、扩展性、可观测性、错误闭环 |
| diff | 文件路径 + 变更摘要 | 能力从无到有、旧问题如何被系统性解决 |
| 日志/测试 | 命令/日志片段/测试结果 | 验证证据、性能/准确率/稳定性变化 |

## 从做得好的内容提炼

不是只找问题，也要从好设计和好实现中提炼亮点：

- 原系统有什么约束或痛点。
- 设计或代码用了什么机制解决。
- 这个机制为什么比普通实现更稳、更可扩展或更可运营。
- 带来了什么效果：可度量、可定位、可解释、可恢复、可扩展。

## 过滤

以下内容即使有源锚点，也不进入能力资产：

- 遵循规范即可避免的 bug。
- AI 未按规则执行导致的返工。
- 单个字段、单个按钮、单个 catch 的补齐。
- 没有系统能力提升的局部修补。

## 输出要求

每个资产必须至少包含一个源锚点。没有锚点的内容只能作为候选，不能写入简历 bullet。
