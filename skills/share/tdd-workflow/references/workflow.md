# TDD 执行流程

## Step 1：确认可测试行为

先从 Spec / SDD / Task Contract / bug 复现中选一个可验证行为，并用一句话写清：

- 要保护的行为是什么
- 最小输入是什么
- 期望输出或可观察结果是什么
- 现有项目用什么测试框架

若行为无法被自动测试表达，说明原因并转 `delivery-workflow` 或 `webapp-testing`。

## Step 2：Red

先写一个会失败的测试：

- bugfix：复现当前 bug
- feature：表达新增最小行为
- contract：固定字段、状态码、序列化、数据库边界
- legacy-safe：先写不改变行为的安全网

必须记录失败摘要。测试无法运行时，标 `blocked` 或 `unknown`。

## Step 3：Green

只写让当前测试通过的最小实现：

- 不顺手重构无关代码
- 不扩大接口或字段范围
- 不补没有测试保护的额外功能

记录通过命令和结果。

## Step 4：Refactor

绿灯后再清理结构：

- 去重复、改善命名、收敛边界
- 不改变测试表达的行为
- 重构后重跑同一测试集

若没有重构价值，说明“不重构”的原因。

## Step 5：Evidence

输出必须包含：

- 上游锚点：Spec / SDD / Task Contract / bug 复现
- Red 失败摘要
- Green 通过摘要
- Refactor 后通过摘要或未重构原因
- 覆盖范围
- 未覆盖风险

## 最小证据表

| 阶段 | 命令 / 产物 | 结果摘要 | 结论 |
|---|---|---|---|
| Red |  | 预期失败： | pass / blocked |
| Green |  | 最小实现通过： | pass / blocked |
| Refactor |  | 重构后仍通过 / 未重构原因： | pass / not_applicable |

## 常见反模式

| 反模式 | 修正 |
|---|---|
| 先写实现再补测试 | 回到 Red，先补可失败测试 |
| 测试一次写太大 | 缩成一个行为一个断言组 |
| 绿灯时顺手大重构 | 先停在最小实现，重构放到 Refactor |
| 只说“测试通过”不给命令 | 输出命令、结果和摘要 |
