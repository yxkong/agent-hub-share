# 子 Agent 两阶段审查协议

> P1 增强协议。仅在主模型已经通过 G1 / R2 判定可以派发子 Agent 后使用；本文件不放宽派发条件。

## 适用边界

- 任务已经有明确范围、验收标准和可审查产物。
- 子 Agent 输出会影响代码、配置、SQL、脚本、skill 或公共规则。
- 主模型仍负责集成、验证和最终判断；子 Agent 结果不是完成证明。

不适用：

- 探索、方案权衡、读代码定位、问答。
- 单文件小改且主模型可直接完成。
- 多个写者会修改同一文件或共享状态。

## 两阶段顺序

1. **规格合规审查**：只看产物是否满足任务原文、范围白名单、验收标准和禁止项。
2. **代码 / 资产质量审查**：规格审查通过后才看可维护性、边界、副作用、命名、测试或文档质量。

硬约束：

- 规格合规未通过，禁止进入质量审查。
- 审查发现问题后，必须由实现者修复，再重新审查；不得用实现者自查代替正式复核。
- 两阶段审查的结论都要进入主模型 integration pass。

## 审查上下文契约

审查者只接收：

- `BASE` / `HEAD` 或明确文件范围。
- 任务原文。
- 验收标准和禁止项。
- 必要的项目技能 / 规范路径。

禁止传入：

- 主模型的完整会话历史。
- 实现者的推理过程。
- “我觉得已经完成”这类结论性引导。

原因：审查者应审 artifact 与 contract，不审协调者的思路。

## 反馈三级处置

| 等级 | 定义 | 处置 |
|---|---|---|
| Critical | 破坏规格、安全、数据、回滚或主链路 | 立即修复并重审 |
| Important | 本任务范围内的正确性、维护性、验证缺口 | 本任务内修复；若暂缓，必须列入 limitation |
| Minor | 不影响本任务交付的小优化 | 记录到回灌项，不阻塞当前主链 |

## 红线

- 禁止并行多个写者改同一文件；并行任务必须有互斥文件所有权清单。
- 禁止把“子 Agent 说成功了”当作 G3 / G4 验证。
- 禁止审查者继承实现者上下文后只做背书。
- 禁止为了跑两阶段审查而扩大任务范围或新增并行真源。

## 主模型 integration pass

最终收口前，主模型必须确认：

1. 规格审查结果已处理。
2. 质量审查结果已处理或进入 limitation。
3. 子 Agent 的 `CONCERNS` 没有被摘要吞掉。
4. 本地验证命令和主链证据仍由主模型汇总。
