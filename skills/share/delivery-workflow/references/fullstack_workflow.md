# 前后端联动 Workflow

## 适用范围

适用于一个需求同时涉及页面、接口、字段、数据库、配置、权限或联调逻辑。

## 第一阶段先解决什么

联动需求最怕返工，所以第一阶段优先解决：

- 业务目标是否已经统一理解
- 页面行为、接口契约、字段语义是否已经冻结
- 主链路先打哪一条，谁先提供稳定契约
- 是否需要 SQL、配置、权限或状态枚举同步调整
- 哪些内容明确不在本轮范围内

只要契约没冻结，就不要前端和后端各自并行开写。

## 执行步骤

1. 先拆成三层：业务目标、接口契约、前后端实现。
2. 先定契约，再分头实现；不要前端和后端各自猜字段。
3. 契约最少明确：路径、方法、入参、出参、字段语义、状态枚举、错误码、权限、分页、主键/strId 规则。
4. 如涉及数据结构变化，先写 `docs/db/dev/<模块名>/` 脚本与变更说明。
5. 后端先打通最小可用接口或 mock 契约，前端再对主链路接入。
6. 联调顺序优先：主查询链路 -> 主提交链路 -> 异常链路 -> 边界链路。若出现 **保存成功但详情/编辑页缺字段**，按 **`missing_data_debug_triad.md`** 与前端一起核对三层（写库 → 读接口 SQL → 响应 JSON），避免只在一端改表象。
7. 联调完成后，再收尾文档、review、计划更新与经验沉淀。

## 设计输出最少要有

- 业务目标
- 前后端冻结契约
- 主链路拆分顺序
- 风险点与回退点
- 验收点

## Fast Path 判断

只有在下面条件同时成立时，联动需求才允许走 Fast Path：

- 契约已经稳定
- 不改 SQL、配置、权限和状态枚举
- 只影响单一前端页面和单一后端接口
- 联调验证路径非常明确

否则默认走 Full Path。

## 必守规则

- 契约未定，不进入并行实现
- 主链路未通，不优先补边角体验
- SQL、配置、权限变化必须前置识别
- 联调失败先回看契约和边界，不先怀疑局部实现细节

## 联调排查规则（联调失败时专用）

联调失败时，按以下顺序排查，不允许跨层跳跃：

```
1. 确认症状层级：前端报错？接口报错？数据层错误？
2. 前端报错 → 先看 Network 请求/响应，确认入参是否符合契约
3. 接口报错 → 先看 Response body 错误码，定位后端抛出位置
4. 数据不对 → 按 missing_data_debug_triad.md 三层排查
5. 每一层检查完毕，确认是否该层问题，再进入下一层
```

**禁止**：前后端同时改代码（一次只改一侧，验证后再改另一侧）。
**禁止**：联调出现问题时扩大改动范围（联调失败不是重构的触发条件）。
