# 排查问题 Workflow

> **AI 排查最大的陷阱：还没找到根因就开始改代码；还没证实范围就扩大了调查。**
> 本文件的唯一目标：用最小范围找到根因，用外科手术修复，不顺手做任何其他事。

## 适用范围

- 现象已发生：报错、接口失败、数据不对、功能不符合预期
- 不适用：新功能开发、重构 → 转对应 `backend/frontend/fullstack_workflow.md`

## 排查四步法（顺序执行，不得跳步）

### Step 1：症状确认（先描述，不读代码）

在任何代码阅读之前，先用一句话精确描述症状：

```
现象：[HTTP 状态码 / 报错信息 / 页面现象 / 数据异常，必须精确，不能模糊]
重现条件：[什么操作触发 / 必现还是偶现 / 触发频率]
最近变更：[最后一次正常的时间点 / 最近合入的改动]
期望结果：[期望是什么]
```

**禁止**：症状描述是"有 bug""功能不对"——这不是症状，是结论。

### Step 2：假设优先（列假设，再找证据）

基于症状，列出 **1-3 个** 最可能的原因，**按可能性排序**：

```
假设 1（最可能）：[具体猜测，如"入参 X 字段为空"，不是"可能是代码问题"]
  → 验证方式：看 [具体日志/断点/接口响应] 中的 [具体字段]
假设 2：[次可能]
  → 验证方式：...
假设 3：[备选]
  → 验证方式：...
```

**不允许**：假设超过 3 个（说明症状还没看清楚，回 Step 1）。
**不允许**：假设内容是"可能有很多地方有问题"（不是假设，是放弃定位）。

### Step 3：最小范围调查（证据驱动，禁止漫游）

**调查起点**：从症状最近的位置开始，不从"可能相关的模块"开始。

| 症状类型 | 调查起点 | 不要先看 |
|---------|---------|---------|
| 接口报错 | 错误日志抛出位置 / Controller 入参校验 | 所有 Service 实现 |
| 接口 200 但数据不对 | 按 `missing_data_debug_triad.md` 三层 | 前端组件、无关表 |
| 前端显示异常 | DevTools Network → Console → 对应组件 | 后端代码 |
| SQL 慢 / 超时 | 执行计划 / 慢查询日志 | 业务逻辑代码 |
| 数据不一致 | 写入链路日志 → 最近 commit 记录 | 整个模块 |

**范围扩大规则**（只有满足条件才允许看下一个文件）：

```
我现在看了 [文件A]，发现 [具体证据]，
这个证据指向 [文件B] 中的 [具体方法/字段]，
所以我需要打开 [文件B]。
```

如果说不出这句话，不允许打开新文件。

**禁止项**：

- ❌ "这个类看起来也可能有问题"（可能性不是证据）
- ❌ "顺便看一下这个文件" （没有顺便）
- ❌ "这段代码写法不对，我改一下"（排查阶段禁止任何非必要修改）
- ❌ 一次打开超过 5 个文件（说明范围失控，先复述当前假设）

### Step 4：外科手术修复（精准，不顺带）

**只修复**被证实有问题的代码。

修复前自检：

```
根因：[用一句话描述确认的根因]
修复点：[具体文件 + 方法 + 行号范围]
修复内容：[改什么，不超过 3 处变更]
不改：[哪些相关的"看起来不优雅"的代码本次不动]
```

**禁止项**：

- ❌ 修复时顺手重构（今天排查，今天只修，重构另立需求）
- ❌ 修复范围超过根因直接影响链（如根因在 Service，不要顺手改 Controller 的参数）
- ❌ 用"改为更好的实现方式"替代"修复具体错误"

### Step 4.5：连续失败时质疑架构

同一问题修复 3 次仍失败，停止继续 patch，回到设计层质疑当前模式。典型信号：

- 同一处反复修，根因却不断漂移。
- 修 A 坏 B，新增修复不断暴露共享状态或隐藏耦合。
- 修复需要越来越多特判，且特判没有稳定边界。
- 为了让补丁成立，必须绕过原交互、状态机或分层语义。

输出最小架构质疑包：

```text
已尝试修复：
失败证据：
怀疑的架构问题：
继续 patch 的风险：
更小的验证/重构候选：
```

未完成这一步，不尝试第 4 次同类修复。

### 并行失败域判定

只有当 2 个以上失败满足以下条件时，才可并行派发排查子 Agent：

- 失败属于不同文件、子系统或输入域。
- 不共享状态、锁、缓存、事务、全局配置或同一输出文件。
- 一个失败的修复不会改变另一个失败的复现条件。

派发 prompt 必含四要素：聚焦域、自包含上下文、约束（例如“不改生产代码”）、要求返回根因和证据摘要。关联失败必须由同一条排查链处理，不拆给多个写者。

## 验证（精准，不扩大）

```
验证步骤：
1. 原症状是否消失？[用 Step 1 的精确描述验证]
2. 相邻功能是否仍正常？[只测直接相邻的，不做全量回归]
3. 修复是否有副作用？[只看修改点的直接下游]
```

## 排查沉淀

排查结束后，评估是否需要沉淀：

| 情况 | 动作 |
|------|------|
| 是已知 bug 类型（如 N+1、幂等缺失、序列化丢字段） | 写入 `checklist.md` 对应验证项 |
| 根因在设计层（如分层错误、职责不清） | 写入 `bad_smell_registry.md` |
| 需要防止同类问题 | 在对应 reference 中补"排查切入点" |
| 一次性 bug，无复用价值 | 不沉淀，不写文档 |
