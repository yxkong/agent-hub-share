# 真实协作算子

> 本文件把“别表演专业性，暴露真实判断”的心法落到研发阶段门。它不是 prompt 模板库，也不收集口语问法；具体可复用 prompt 只有在 R3 判定为高复用提示词资产时才转 `prompt-engineering`。

## 目标

- 防盲改：先形成可验证假设，再读代码或改代码。
- 防装懂：把不确定点、验证方法、残余风险说清楚。
- 防过度设计：先证明最小方案不足，再升级设计或重构。
- 防漏验：在交付前暴露边界、失败链路和最可能返工点。
- 防失败浪费：返工后把原因落到 rule / checklist / test / prompt / insight。

## 算子总表

| 算子 | 解决的问题 | 触发阶段 | 最小输出 |
|------|------------|----------|----------|
| Hypothesis First | 防止一上来乱改 | Debug / Gate 1 | 1-3 个有序假设 + 最近证据入口 |
| Uncertainty Exposure | 防止不知道还装知道 | Gate 1 / Gate 2 | `fact / assumption / unknown / risk / next check` |
| Smallest Viable Change | 防止范围膨胀 | Gate 2 / Gate 3 | 最小可行改法 + 不改范围 |
| Behavior Mode Change Confirmation | 防止排查时顺手改变运行语义 | Gate 2 / Gate 3 | 原模式 vs 新模式 + 用户确认 |
| Refactor Burden of Proof | 防止动不动重构 | Gate 2 | 为什么局部改不够 + 触发的结构性证据 |
| Adversarial Review | 防止方案自嗨 | Gate 2 / Gate 4 | 反方视角下最可能失败点 |
| Risky Test Design | 防止只测主链路 | Gate 4 | 最容易漏测的边界 / 失败 / 回归用例 |

## 执行规则

### Hypothesis First

触发：报错、数据异常、功能不符合预期、线上现象复盘。

要求：

- 改代码前先列 1-3 个按概率排序的根因假设。
- 调查入口必须贴近症状：报错行、HTTP 响应、日志、DB 行、页面状态或最近一次变更。
- 每打开一个新文件，都要能说明它和假设的关系。

禁止：

- 从模块顶层泛读。
- 没有假设就批量改多个文件。

### Uncertainty Exposure

触发：需求不完整、接口/字段/权限不明、上下文可能过期、验证条件不足。

要求：

- 影响下一步时，显式分开 `fact / assumption / unknown / risk`。
- 对每个关键 unknown 给出最小验证动作。
- 不能验证时，说明本轮结论的可信边界。

禁止：

- 用确定口吻包装未验证推断。
- 为了显得完整而隐藏跳过的检查。

### Smallest Viable Change

触发：优化、修复、联调、补字段、补边界。

要求：

- 先说最小有效改法，再说更完整方案。
- 明确不改范围，尤其是接口契约、数据结构、权限、状态机、公共组件。
- 实现时一次只推进一个最小闭环。

禁止：

- 借小问题顺手重排目录、换框架、改公共抽象。

### Behavior Mode Change Confirmation

触发：任何改变系统交互模式、行为模式、架构风格或运行语义的改动。

典型例子：

- 异步改同步，或同步改异步。
- Kafka / MQ / event-driven 改为直接调用、轮询、内存队列或本地事务内处理。
- DDD 分层、端口适配、领域服务、仓储边界被改成其他架构风格。
- 状态机、幂等、重试、补偿、事务边界、最终一致性语义发生变化。
- 前端交互从显式确认改为自动提交，或从后台任务改为阻塞等待。
- 为了排查缺数据、缺轨迹、回显异常，把原有链路绕过或短路。

要求：

- 改之前必须列出：当前模式、新模式、行为差异、兼容风险、验证路径、回滚方式。
- 必须取得用户明确确认后才能实现；用户明确说“直接执行 / 按这个改 / 不用确认”时可继续，但仍要一句话声明风险。
- 排障任务默认保持原运行语义，只定位断点和补证据；不能把架构模式变更当作修复。

禁止：

- 在用户只要求排查、补日志、补轨迹、修 bug 时，顺手把异步链路改成同步链路。
- 以“更简单”“更稳定”“更容易验证”为理由，绕过原有架构约束。

### Refactor Burden of Proof

触发：提出重构、抽象、拆模块、统一框架、批量替换。

要求：

- 先证明局部修改不足：重复已经影响正确性、边界无法表达、测试无法覆盖、扩展点已真实出现。
- 给出不重构方案的失败点，以及重构方案的回滚/验证路径。

禁止：

- 因为“更优雅”“更高级”“以后可能用到”而扩大改动。

### Adversarial Review

触发：方案收敛前、交付前、用户觉得“好像不对但说不上来”。

要求：

- 用反方视角指出最可能返工的地方。
- 优先看契约错位、边界遗漏、权限/租户、安全、状态同步、保存后回显、缺数据链路。
- 如果反方检查发现 P0 风险，回到 Gate 2 或 Gate 4，不直接宣称完成。

禁止：

- 只总结方案优点。
- 把未验证风险写成“后续优化”。

### Risky Test Design

触发：实现完成前、修 bug 后、准备交付前。

要求：

- 除主链路外，至少点名最容易漏测的边界或失败链路。
- 常见风险维度：空值、重复、越界、脏数据、旧数据、权限、租户、并发、重试、失败回滚、响应体缺字段。
- 测试选择遵循最小安全验证，不把 Fast Path 强行扩大成全量回归。

禁止：

- 只用“已跑通”替代响应体、页面状态或 DB 证据。

## 与 R3 的关系

出现失败、返工或低分时，先按 `delivery-workflow` R3 归因：

- 如果是认知洞察：转 `project-insight-extractor`。
- 如果是 Agent 反模式或阶段门缺口：回填 SKILL / checklist / anti-pattern。
- 如果是可复用高质量任务提示词：再转 `prompt-engineering` 写 `prompts/share/**`。

不把一次性口语问法直接沉淀为 prompt 资产。
