# 后端开发 Workflow

## 适用范围

适用于领域能力新增、接口开发、持久化改造、策略扩展、缓存、任务、权限、审计、SQL 调整。

## 第一阶段先解决什么

先不要急着写接口或改表，先解决下面问题：

- 业务真正要新增、修复或约束什么能力
- 影响哪些领域对象、接口、表、状态和上下游
- 哪些输入输出、异常、权限、租户、事务约束必须先定
- 是否需要数据变更、脚本或配置变更
- 哪些边界明确不改

如果这些问题没收敛，先做领域与契约设计，不直接编码。

## 执行步骤

1. 明确业务目标、边界和不改范围。
2. 确认涉及模块、领域对象、表、接口、上下游依赖。
3. 先设计领域与契约：入参、出参、状态、异常、权限、租户、事务边界。
4. 如涉及数据变更，先明确是否需要 `docs/db/dev/<模块名>/` 脚本。
5. 按最小闭环实施：先打通主链路，再补扩展点、缓存、日志、灰度、性能优化。主链路通常是主接口或主流程。
6. 做最小验证：接口成功、失败、边界、事务、权限、租户、分页、幂等。若「成功但缺字段」，必须验 **HTTP 响应体** 而非仅日志，并按 **`missing_data_debug_triad.md`** 区分写入 / 查询 / 序列化出口。
7. 补充文档、配置、SQL 说明。
8. 若过程踩坑，评估是否沉淀到规则、模板、测试或技能 reference。

## 设计输出最少要有

- 业务目标
- 领域对象与职责
- 接口契约
- 数据影响面
- 风险点
- 验收点

## Fast Path 判断

满足下面条件时，可以快进到实现：

- 只改单一接口或单一逻辑分支
- 不改表结构、不改核心状态机
- 不影响跨模块契约
- 验证路径清楚

否则先补设计。

## 排查场景跳转

**任务是排查问题（报错 / 数据不对 / 功能不符合预期）时**，先读 `debug_workflow.md`，再回本文件定位修复点。

排查中的额外禁止：
- 在还未定位根因前，不修改任何代码
- 排查日志 / 接口时，只看症状最近的调用链，不从顶层模块扫起
- 找到根因后，修复范围严格限定在根因直接影响链内
