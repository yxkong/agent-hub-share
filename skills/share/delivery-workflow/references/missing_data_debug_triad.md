# 「接口成功但缺数据」三联检（保存 / 查询 / 封装与序列化）

适用于：**HTTP 200 或业务 `status=1`，但页面或下游仍看不到某字段**（能力、价格、扩展 JSON、关联子表等）。三层往往**同时值得怀疑**，不要只盯其中一层。

---

## 层 1：有没有真正保存成功

**目的**：区分「请求没报错」与「持久化与业务预期一致」。

- **不要**把「接口返回成功」直接等同于「子资源也写入了」（常见：主表 `modify` 成功，价、能力、扩展表未写或未提交事务）。
- **核对**：事务边界、Gateway 是否对子表静默 no-op、租户 / 软删 / 主键是否与写入条件一致。
- **验证**：写后读库（同环境）、或写后立刻调只读查询；必要时打 SQL / 断点看 `INSERT`/`UPDATE` 是否发生。

---

## 层 2：查询有没有查到

**目的**：区分「库里有」与「读模型没带出来」。

- **核对**：`detail` / `find_by_id` 是否只做主表、忘记二次查询子表；`WHERE` 是否多加了 `tenant_id`、`deleted` 导致查不到；关联键 `model_id` 是否与写入一致。
- **验证**：与接口等价的查询在 DB 或 REPL 跑一遍；对分页列表与详情分别验（列表常省略关联字段）。

---

## 层 3：有赋值逻辑，是不是封装 / 序列化链路丢了字段

**目的**：区分「内存里已有」与「HTTP JSON 里真有」。

典型坑（本项目曾踩全）：

1. **实体/DTO 上的「非表列」字段**用 `PrivateAttr` + `@property` 承载，**默认不参与** `model_dump` / OpenAPI 字段集，详情响应里「没有该键」。
2. **统一响应体**（如 `ResultBean.success`）若先把 `data` **`model_dump` 成 `dict` 再赋回**，而 `data` 的类型仍标注为 **Pydantic/SQLModel 类型**，则在 **FastAPI `response_model` + 二次序列化** 时会出现：类型与实例不一致、扩展字段被剥、`model_serializer` 收到错误 `self`（例如 `dict`）导致异常或丢字段。
3. **请求体**字段未在 Command 上声明，入参被丢弃，写库逻辑从未执行（与层 1 联动）。

**验证**：从 **Controller 返回值** 一路跟到 **实际 HTTP body**（浏览器 / curl / `TypeAdapter` 序列化）；对「装箱 + 泛型 + `response_model`」路径重点怀疑；遵守项目 **B-022**：响应不要无谓手写 `model_dump`，避免与统一响应封装打架。

---

## 使用顺序与停止条件

1. 先快速判定更可能在哪一层（是否刚改过写入 / 刚改过查询 / 刚改过 DTO 与 `ResultBean`）。
2. **每层用独立证据闭环**（日志不够时上 DB 或序列化单测），再进入下一层。
3. 若三层都排除，再查前端映射、缓存、代理脱敏等外围因素。

---

## 失败沉淀归类（便于 Gate 6）

| 典型根因           | 多归入           |
|--------------------|------------------|
| 子表未写、事务未提交 | 验证不足 + 设计漏项 |
| 查询条件过严、漏关联 | 验证不足 + 契约不清 |
| 响应装箱 / 序列化丢字段 | **验证不足**（未把「出口 JSON」纳入验收）+ 切分不当（未把响应链列为同一闭环） |

将本文件与项目规则 **B-022**、统一响应体实现对照，可避免同类返工。
