# 前端开发 Workflow

## 适用范围

适用于页面新增、CRUD 改造、表单/表格/弹窗/抽屉、展示逻辑优化、交互修复。

## 第一阶段先解决什么

先不要急着画页面或改组件，先解决下面问题：

- 用户真正想完成什么任务
- 入口页面和核心操作链路是什么
- 成功状态、失败提示、空态、权限态分别是什么
- 是否依赖后端契约，如果依赖，哪些字段还没定
- 哪些地方明确不改

如果这些问题没收敛，先做页面设计，不直接编码。

## 执行步骤

1. 明确页面目标、用户场景、边界和不改范围。
2. 确认页面归属项目与模块，不要一开始改错仓库或子应用。
3. 收集当前页面、关联组件、API、字典、权限入口和状态来源。
4. 先做页面设计：信息架构、交互流程、状态切换、错误提示、空态与权限态。
5. 如依赖后端接口，先确认接口契约；契约不稳时不要先硬写页面细节。
6. 按最小闭环实现：先打通主链路，再补弹窗、联动、边角状态。主链路通常是列表、详情或主提交流程。
7. 做最小验证：渲染、查询、分页、提交、错误提示、权限显示、主状态切换。
8. 如涉及文档或配置说明，落到 `docs/` 对应目录。

## 设计输出最少要有

- 页面目标
- 页面入口与影响范围
- 主交互链路
- 关键状态与交互
- 依赖接口清单
- 验收点

## Fast Path 判断

满足下面条件时，可以快进到实现：

- 只改单个页面或单个组件
- 不改接口字段契约
- 状态流转不变
- 验证方式非常清楚

否则先补设计。

## 排查场景跳转

**任务是排查前端 bug（样式异常 / 数据不显示 / 交互失败）时**，先读 `debug_workflow.md`，再回本文件定位修复点。

排查起点规则：
- 先看 DevTools **Network**（接口返回值）→ **Console**（JS 报错）→ 再看组件代码
- Step 3 的"收集当前页面/组件/API"在排查时**只收集症状直接相关的**，不全量收集
- 接口返回正确但页面不显示 → 先查组件的数据绑定，不先改接口
