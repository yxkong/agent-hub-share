# 行为验证（Behavioral Eval）

适用于高风险、纪律执行类、容易被合理化绕过的 skill。目标不是验证“文档看起来对不对”，而是验证“skill 是否真的改变了 Agent 的默认行为”。

## 何时使用

优先用于以下 skill：

- 明明知道规则，但在赶时间时仍可能跳过的 skill
- 命中后若不遵守，会造成返工、误改或漏验的 skill
- 用户目标与规范动作天然冲突的 skill，例如“快点做完”与“先验证 / 先设计 / 先读 skill”

通常不必使用：

- 纯参考类 skill
- 结构治理 / 目录治理类 skill
- 只负责 catalog、layout、挂载约束的 skill

这类 skill 仍以结构验证、效果验证、触发验证为主。

## 核心原则

- 先看无 skill 时会怎么做，再看加 skill 后有没有变化
- 记录真实借口，不要自己脑补失败原因
- 让场景逼迫 Agent 做选择，不要只问“你应该怎么做”
- 行为验证是增强门，不替代 `eval_playbook.md` 的基础验证

## 四步法

### 1. 建基线

在**不提供该 skill**的前提下，给 Agent 一个接近真实工作的任务，观察它会不会直接走老习惯。

记录：

- 它选了什么动作
- 它为什么这么选
- 它用了哪些原话级别的合理化借口

### 2. 加 skill 复测

在相同或近似场景下提供 skill，再看它是否：

- 主动执行正确动作
- 引用了 skill 中真正关键的约束
- 不再重复基线里的借口

### 3. 比对前后差异

重点比较：

- 是否从“直接开干”变成“先做前置动作”
- 是否从空泛解释变成引用具体规则 / SOP / 红线
- 是否减少了错路、跳步、无效扩读

### 4. 堵漏洞

如果 Agent 还是会绕过 skill：

- 把借口逐字记录下来
- 追问是 description 不准、正文不清、还是规则不够显眼
- 只补最小必要内容，不用借机把 skill 写厚

## 场景设计

好的行为验证样本应满足：

- 是真实会发生的工作情境，而不是学术问答
- 要求 Agent 做决定或执行，而不是复述概念
- 约束具体，例如时间、返工成本、审查压力、已有工作量
- 若是纪律执行类 skill，优先给 2~3 个组合压力，而不是单一压力

优先使用这些压力来源：

- 时间压力：今晚要交、窗口快关闭
- 沉没成本：已经做了不少，删掉很痛
- 速度偏好：用户/同事明显更想快一点
- 权衡冲突：质量动作会拖慢当前目标

## 成功标准

高风险 / 纪律类 skill 至少满足：

- 一轮基线样本能看出默认错误倾向
- 一轮带 skill 的复测样本能看出行为发生改变
- Agent 的理由从“常识 / 经验判断”变成“引用 skill 约束”
- 至少识别并记录 1 条真实合理化借口

如果只是“答对了概念题”，但行为没有变化，不算通过。

## 常见误用

- 把行为验证当成所有 skill 的强制门禁
- 用明显无关的负例凑样本
- 自己替 Agent 总结借口，而不是记录原话
- 一次通过就结束，不看是不是场景太弱
- 借行为验证之名，把 skill 主文件继续写厚

## 产出要求

完成一次行为验证后，至少留下：

- 1 条基线样本
- 1 条带 skill 的复测样本
- 1 条真实合理化借口
- 结论：问题在 description、正文结构、SOP，还是红线表达
