# 从存量代码与老项目中提炼 Skill / SOP

适用于：

- 现有项目没有成体系 skill
- 文档不完整，主要依赖代码逆向理解
- 目标不是先写漂亮文档，而是先提炼出能驱动开发的最小资产

## 先做 30 秒判断

只有当本次任务属于下面情况时，才走本文件：

- 要从代码 / 主文档中提炼 skill
- 要从存量系统抽研发 SOP
- 要让 AI 后续能据此更快开发，而不是仅仅做项目介绍

如果你现在主要是在推进一个真实需求开发，而不是沉淀 skill 资产，请转 `delivery-workflow`。

## 核心目标

这条路的目标不是直接产完整 full skill。

默认目标是先提炼出“最小可驱动产物”：

- 边界
- 主链路
- 高频切入点
- 最小 SOP
- 最小验证方式

只有当这 5 项已经稳定，才考虑继续扩成 `standard` 或 `full`。

## 证据优先级

提炼时按这个顺序取证：

### P0

- 当前主链路代码
- 当前真实入口
- 当前主配置
- 当前主调用链

### P1

- 当前主文档
- 当前接口定义
- 当前有效 skill

### P2

- 历史文档
- 历史 skill
- 备份、副本、旧说明

冲突处理固定遵循：`P0 > P1 > P2`。

## 快速定位四步法

提炼时默认按这 4 步走，不要反过来：

1. 先找入口
2. 再找主链路
3. 再找高频变更点
4. 最后才补规则、示例和扩展知识

## 配套 Prompt 模板

> 每个步骤需要"精确引导 AI 分析"时，直接从 [extraction_prompt_template.md](extraction_prompt_template.md) 取对应 Prompt 发给 AI：
> - **Step 3（追主链路）** → Phase 1 代码分析 Prompt
> - **有设计文档时** → Phase 2 设计文档分析 Prompt
> - **Step 6（补验证）** → Phase 3 技能验证 Prompt

## 提炼步骤

### Step 1：盘边界

先看：

- 仓库根目录与子工程
- 模块边界与启动入口
- 常见分层：controller / service / manager / dao / client / job / listener

输出：

- 模块边界列表
- 入口层 / 业务层 / 基础设施层的初步划分

### Step 2：找真实入口

优先找：

- `*Controller`
- `*Job`
- `*Listener`
- `*Consumer`
- RPC / Feign / Dubbo / gRPC 入口
- 脚本、批处理、命令入口

输出：

- 真实入口列表
- 入口类型
- 入口类 / 方法 / 文件

### Step 3：追主链路

沿入口往下追：

`入口 -> Service -> Rule / Strategy -> DAO / 表 -> 外部系统`

每追一层都记录：

- 当前职责
- 下一跳是谁
- 关键数据是什么
- 状态在哪里变化

输出：

- 1 条主链路
- 必要时补 1 条失败链路或异常链路

### Step 4：找高频变更点

重点找这些位置：

- 枚举
- 配置 key
- 策略 / 工厂 / 路由
- 抽象接口与实现类
- 校验器
- 异常处理入口
- 日志表、状态表、结果表

输出：

- “新增 / 修改 / 对接 / 排查”四类场景的候选切入点

### Step 5：抽最小 SOP

重点回答：

- 新增一个类似能力时先看哪里
- 修改规则时先看哪里
- 对接外部系统时先过哪些环节
- 排查问题时先查哪条链路
- 验证改动时怎么验

输出：

- 4 到 8 步的最小 SOP
- 每一步必须是可执行动作，不写空泛描述

### Step 6：补验证

至少设计 1 到 2 条真实任务验证：

- “新增一个渠道 / 规则 / 类型时应改哪”
- “排查失败 / 重复 / 状态异常时应先查哪”

如果回答仍然抽象，先回去补入口、主链路和切入点，不要先润色文档。

### Step 6.5：补闭环承诺映射

从存量项目提炼 skill 时，必须判断项目文档或代码是否已经承诺以下能力；命中则把对应闭环写入提炼结果，未命中则标 `out_of_scope`，不要虚构：

| 承诺能力 | 提炼时必须落到哪里 |
|---|---|
| 交付验证 / 运行证据 | 最小验证方式需标证据等级：`static / contract / runtime / user-visible / release / limitation` |
| 发布 / 回滚 / 观测 | 记录 `Release Evidence`：观察窗口、观察入口、回滚触发条件；若项目无发布面，标 `N/A` |
| 失败学习 / 返工治理 | 记录 `Task Replay Lite`：触发输入、缺失证据、误判 gate、回填位置 |
| 重复误触发 / SOP 失效 | 形成 `Skill Health Signal`，回填 bad smell / trigger eval / design principles |
| 备份脚本 / 备份契约 | 验收命令包含 `check-backup-policy`（仅在命中备份相关能力时） |

## 可用标准

只有满足下面条件，才允许把提炼结果作为后续开发 skill 使用：

- 真实入口可定位
- 主链路可复述
- 至少 3 个高频场景有切入点
- 至少 1 个真实任务可验证

## 冲突处理

遇到冲突时必须这样做：

- 文档与代码冲突，优先代码
- 多实现并存，优先当前主调用链
- 找不到主链路，不允许虚构规则
- 不确定内容写成 `assumption` 或 `unknown`

## 提取结果验收样例

### 合格样例

下面这种提取结果，通常已经能驱动开发：

```md
- 边界：订单履约能力主要落在 order、fulfillment 两个模块，本次新增只涉及 fulfillment。
- 主链路：FulfillmentController.submit -> FulfillmentService.submit -> RuleRouter.route -> FulfillmentOrderMapper.insert。
- 高频切入点：新增状态看 `FulfillmentStatusEnum`；改路由规则看 `RuleRouter`；排查失败单看 `FulfillmentService.failOrder`。
- 最小 SOP：先从 `FulfillmentController.submit` 看入口，再追 `RuleRouter.route`，最后验 `fulfillment_order` 表和失败日志。
- 最小验证：新增一个履约类型时，应同时改枚举、路由和入库映射。
```

特点：

- 有真实入口
- 有主链路
- 有具体切入点
- SOP 是动作，不是口号
- 验证任务能落地

### 不合格样例

下面这种提取结果，不能直接驱动开发：

```md
- 系统采用分层架构，整体比较清晰。
- 业务主要由 controller、service、dao 组成。
- 新增功能时一般修改 service 层。
- 如有问题请结合业务理解后调整。
```

问题在于：

- 没有真实入口
- 没有主链路
- 切入点过于抽象
- SOP 不可执行
- 不能指导真实改动

## 好的提炼结果长什么样

### 最小可驱动包

- 边界：系统 / 模块 / 子模块边界
- 主链路：入口到核心处理到落库 / 外部系统
- 切入点：新增 / 修改 / 对接 / 排查 的高频入口
- 最小 SOP：AI 先看什么、再改什么、最后怎么验
- 最小验证：至少 1 条真实任务

### 不合格信号

- 只有抽象原则，没有真实入口
- 只有架构介绍，没有主链路
- 只有全局说明，没有高频切入点
- 只有格式正确，没有真实验证

## Step 7：反馈沉淀（必做，不可省略）

提炼结果通过可用标准后，路由结束前执行以下步骤：

1. **坏味道检查**：回顾本次提炼过程，是否出现以下信号：
   - 找不到真实入口，最终只能写抽象描述
   - 主链路追踪中断，依赖猜测填补
   - 高频切入点与实际代码对不上，需要后续修正
   - 命中信号则按格式追加到 `bad_smell_registry.md`（草案区），已有条目计数 +1
2. **N=2 提升**：若某条模式已达 2 次，立即提升至 `design_principles.md §六 反模式`
3. **技能更新判断**：若本次提炼发现 skill 的切入点已过期（类名/方法名不存在），当场修正并更新头部 `updated` 字段
4. **入口与可见性**：若本次产出或修改了 hub 内 `SKILL.md` / 新 skill 目录，按 `review/engineering_completion_gate.md` 执行 **§1–§5**

以上完成，本次 extract 路由正式结束。
