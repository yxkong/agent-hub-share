# 代码库证据视图

> 本文件服务 `skill-engineering/extract`。目标不是写一篇架构介绍，而是把陌生仓库的当前代码事实压缩成可驱动开发的项目技能。

## 1. 六类证据视图

| 视图 | 必须回答 | 最小证据 |
|---|---|---|
| 逻辑架构 | 谁负责什么、边界和扩展点在哪里 | 分层职责、禁止依赖、核心抽象 |
| 实现/模块 | 代码在哪里、模块如何依赖 | 根模块、启动入口、3–5 个关键文件 |
| 业务流 | 用户动作如何进入系统并完成业务目标 | 入口 → 编排 → 规则 → 持久化/外部系统 |
| 数据流 | 数据从哪里来、如何转换、在哪里改变状态 | Command/DTO/Context/Entity、表、消息、缓存 |
| 运行过程 | 同步/异步、事务、错误和重试如何传播 | 调用时序、事件/Consumer、失败出口 |
| 横切与外部边界 | 权限、租户、日志、配置、外部 API 在哪里收口 | 拦截点、配置真源、Port/Gateway/Client |

逻辑视图优先，但不能用目录树冒充架构；实现视图必须回到当前文件、类、方法和调用链。

## 2. 陌生仓库读取顺序

1. **定问题与范围**：明确要提炼哪个项目/模块、给哪类开发任务使用；列白名单、黑名单和 unknown。
2. **盘模块与入口**：识别启动入口、Controller/Handler/Job/Listener/Consumer/CLI，以及项目已有设计真源。
3. **追一条业务主链**：只跟主分支，记录每一跳职责、关键数据、状态变化，直到 DB、消息、文件或外部 API。
4. **补数据与失败链**：记录协议模型 → 内部模型 → 持久化模型的转换；补至少一条异常、重试或补偿路径。
5. **找扩展点和高频变更点**：策略、工厂、路由、注册表、配置 key、枚举、校验器、Gateway/Port。
6. **反查边界**：权限、租户、事务、缓存、日志、可观测、配置不能被误写成业务层。
7. **映射到项目技能**：把稳定事实写成边界、路由、最小 SOP、反模式和验证；语言/框架细节只进入项目技能。

## 3. 项目技能最小产物

```text
项目边界:
逻辑架构:
模块/入口:
业务主链:
数据流与状态变化:
失败链:
扩展点/高频变更点:
横切约束:
新增/修改/对接/排查 SOP:
验证命令与判据:
unknown / limitation:
```

若项目采用 DDD，必须从当前代码验证 Adapter/Application/Domain/Infrastructure 或等价职责；不得把共享概念直接当成项目事实。Java、Python、Vue、AI Runtime 等实现约束转入对应 project skill。

## 4. 停止条件

命中任一项时停止提炼并标 `NEEDS_CONTEXT`，不得补猜测：

- 找不到真实入口或主调用链。
- 文档与当前代码冲突且无法确认当前主实现。
- 无法确认数据真源、事务边界或外部契约。
- 多套实现并存，无法证明哪套仍在运行。
- 只有目录和抽象原则，不能回答“新增/修改/排查先改哪里”。

## 5. 与其他能力交接

- 已进入真实需求实现 → `delivery-workflow`。
- 存在架构方案取舍 → `ai-development-governance` ADR。
- 项目文档落位与备份 → `doc-script-governance`。
- 提炼完成后的 skill 结构、trigger 和验证 → 回到 `skill-engineering` 完成门。
