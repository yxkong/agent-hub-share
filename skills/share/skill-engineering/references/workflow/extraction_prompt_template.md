# 技能提炼 Prompt 模板库

**三阶段覆盖"设计→代码→验证"完整闭环。** 在 `extract` / `create` 路由中，按阶段选用对应 Prompt 发给 AI，输出物直接写入 skill references。

## 使用导航

| 阶段 | 适用时机 | 使用 Prompt |
|------|---------|-------------|
| Phase 1：代码分析 | 已有源码，要提炼主链路/切入点/反模式 | §Phase 1 |
| Phase 2：设计文档分析 | 有设计文档/需求文档，要提炼约束/接口契约 | §Phase 2 |
| Phase 3：技能验证 | Skill 已写好，要验证它能否真实驱动 AI 开发 | §Phase 3 |

三个阶段可独立使用，也可按顺序串联（设计→代码→验证）。每个 Prompt 的输出物直接作为 skill `references/*.md` 的内容。

## Phase 1：代码分析 Prompt

> 目标：从源代码提炼 Skill 的主链路、触发关键词、切入点、反模式。

```
你是一名资深架构师，任务是从以下源代码中提炼一份可驱动 AI 开发的 Skill 技能文档。

## 分析维度

**1. 边界与触发（When to Use）**
- 这个模块/功能解决什么核心问题？（一句话）
- 哪些操作会触发这里的代码？列出精确触发词：
  - 类名（如 `AiChatDispatchServiceImpl`）
  - 方法名（如 `resolveSourceId`）
  - 表名（如 `ai_model_capability`）
  - API 路径（如 `/api/ai/chat`）
- 哪些场景明确不属于此模块？（划定边界，指明应转哪里）

**2. 核心机制（How It Works）**
- 最关键的类/接口是什么？职责边界是什么？（一行一个，不超过 8 个）
- 数据流：从入口到输出的完整路径（`入口 → 处理 → 副作用 → 输出`）
- 隐藏行为：幂等/权限/降级/异步分支等不明显但重要的逻辑

**3. 开发者改动 SOP（How to Do）**
- 最高频的 3-5 个改动场景是什么？（如"新增策略实现""修改路由规则""排查失败"）
- 每个场景的最小步骤：先看哪 → 再改哪 → 最后验证哪
- 每步必须有可观测的中间产物（不写"处理完成"这种空泛描述）

**4. 反模式与陷阱（What NOT to Do）**
- 最常见的 3-5 个错误用法（已知的或代码注释中警告过的）
- 每个反模式对应的正确做法
- 违反后的实际后果（数据不一致？性能下降？事务失效？）

## 输出格式

输出一份 Markdown 文件，包含以下 5 个部分，语言用中文：

**主题句**（第一行）：本文件管理什么，一句话说清楚。

**触发关键词表**：精确到类名/方法名/表名/API，用于写入 skill description。

**主链路**（Mermaid flowchart）：从真实入口到核心处理到输出，标注关键类名。

**改动 SOP 表**（Markdown 表格）：
| 场景 | 先看哪 | 改什么 | 验证点 |
|------|--------|--------|--------|

**反模式清单**（Markdown 列表）：
- ❌ 错误做法 → ✅ 正确做法 → ⚠️ 违反后果

控制在 80-150 行之间，禁止大段转述代码，重点解释"为什么"和"怎么做"。
```

## Phase 2：设计文档分析 Prompt

> 目标：从设计文档、需求文档、ADR 中提炼约束、接口契约、决策理由，产出 `dev_hardlines.md` 或 `anti_patterns.md` 的内容。

```
你是一名架构师，任务是从以下设计文档/需求文档中提炼可以写入 Skill 的约束性内容。

## 分析维度

**1. 业务不变量（Invariants）**
- 什么是绝对不能打破的业务规则？（如"同一订单不能被两个渠道同时处理"）
- 什么是系统的核心假设？（如"tenant_id 在整个请求链路中不可变"）
- 用"禁止 X，否则 Y"的格式表达每条不变量

**2. 接口契约（Contracts）**
- 哪些 API/接口是对外契约，不能随意改变的？
- 每个对外接口的：入参约束、出参约束、错误码语义
- 数据模型中哪些字段是核心语义（改了会破坏上下游）？

**3. 决策理由（Why This Design）**
- 这个设计解决了哪些已知的"错误方案"？
- 已被讨论和否定的替代方案有哪些？为什么否定？
- 这些理由要变成 Skill 中的"硬规则"，防止 AI 重踩

**4. 风险边界（Danger Zones）**
- 哪些操作一旦执行就不可逆？
- 哪些场景下 AI 最容易做出错误判断？
- 需要人工介入/审批的操作有哪些？

## 输出格式

输出两个部分：

**硬约束清单**（直接写入 skill 的 `hardlines` 或 `dev_hardlines.md`）：
每条约束格式：`[约束ID] **禁止/必须** 描述 → 违反后果`

**决策背景速查表**（防止 AI 重踩历史坑）：
| 决策 | 否定方案 | 否定理由 |
|------|---------|---------|

语言用中文，约束条目不超过 15 条，每条必须是可验证的（"不能有歧义"）。
```

## Phase 3：技能验证 Prompt

> 目标：用一个真实任务验证 Skill 是否能真实驱动 AI，找出缺失的切入点和过期内容。

```
你是一名 Skill 质检员，任务是用提供的 Skill 完成一个具体改动，评估 Skill 的可用性。

## 待验证任务

[在此处填入具体任务，例如："在 <runtime-module> 中新增一个 ReAct 工具，工具名叫 get_stock_price，需要支持 tool_call 调用。"]

## 验证规则

**规则 1：只用 Skill，不用记忆**
- 读 Skill 主文件，选择路由
- 读对应 reference 文件
- 不依赖任何 Skill 之外的知识

**规则 2：逐步记录**

Step 1 - 定位入口（30 秒内能否找到要改的文件/类/方法？）
- 找到了：记录入口位置
- 找不到：说明哪个环节的 Skill 内容不够具体

Step 2 - 执行 SOP（按 Skill 中的步骤操作）
- 每步的实际产物是什么？
- 有没有 SOP 未覆盖的情况？
- 有没有 Skill 中描述的内容与实际代码不符？

Step 3 - 验证结果（改动是否产生了预期效果？）
- 预期的可观测产物是否出现？
- 是否有意外副作用？

## 输出格式

```
验证结论：[PASS / PARTIAL / FAIL]

入口定位：[OK: 文件/类/方法] 或 [MISS: 缺少哪类信息]

SOP 执行：
- Step N: [OK/MISS/OUTDATED] 具体说明

过期内容：[类名/方法名已不存在的条目]

缺失内容：[建议补充到哪个 reference 文件]

bad_smell 信号：[是否触发以下类型：SOP空泛 / 内容无效 / 切入点过期]
```
```

## 代码文件选取建议

按模块类型选择要送入 Phase 1 Prompt 的代码文件：

| 模块类型 | 建议阅读的关键文件 |
|---------|-----------------|
| 通用模块 | 抽象基类 `Abstract*.java`、接口 `I*.java`、核心配置 `*Configuration.java` |
| 执行器/服务 | `*ExecutorImpl.java`、`*ServiceImpl.java` |
| 路由/策略 | `*Router*.java`、`*Strategy*.java`、`*Factory*.java` |
| 消息/事件 | `*Listener.java`、`*Consumer.java`、`*Handler.java` |
| 基础设施 | `*GatewayImpl.java`、`*Mapper.java` + 对应 XML |
| 前端组件 | 核心组件 `*.vue`、`composition/*.js`、`api/*.js` |

## 产出物存放规范

| 阶段产出 | 存放位置 |
|---------|---------|
| Phase 1 产出（主链路/SOP/反模式） | `references/{模块名}.md` 或对应 BX/RG 文件 |
| Phase 2 产出（硬约束/决策背景） | `references/dev_hardlines.md` 或 `references/anti_patterns.md` |
| Phase 3 产出（验证报告） | 不单独存档；过期条目当场修正，bad_smell 追加到 `bad_smell_registry.md` |
