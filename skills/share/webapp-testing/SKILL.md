# Webapp Testing

## 作用边界

本技能只负责一件事：

- 用浏览器自动化和黑盒验证方式，验证本地 Web 应用是否按预期工作

本技能不负责：

- 设计前端页面视觉风格
- 推进业务需求的设计与切分
- 替代单元测试、接口测试或后端契约设计
- 从存量代码提炼技能资产

## 何时使用

当用户要验证、排查或复现本地 Web 应用问题时，优先使用本技能：

- 验证前端页面主链路是否可用
- 用浏览器自动化复现 UI bug
- 采集截图、控制台日志、网络错误
- 联调后做最小可验证回归
- 在不深读源码的情况下先黑盒确认问题

## 30 秒决策区

先判断当前属于哪一类：

- 静态 HTML：可先直接看 DOM 或 `file://` 页面，再写最小自动化脚本
- 本地动态应用：优先确认本地服务是否已启动，再做浏览器侦察
- 已有自动化或启动脚本：先把它们当黑盒工具用，不先读源码

默认先走“侦察 -> 动作 -> 验证”，不要一上来就写长脚本。

## 核心原则

- 先黑盒验证，再决定是否需要深读代码
- 先侦察渲染后的真实 DOM，再写选择器
- 先主链路冒烟，再补失败链路和边界链路
- 优先复用已有启动脚本、测试脚本、helper，而不是重新造一套
- 有现成脚本时，先看 `--help` 或最小用法，不先读大脚本源码

## 标准流程

### 1. 启动与环境确认

先确认：

- 页面是静态 HTML 还是动态应用
- 前端服务是否已启动
- 是否依赖后端、Mock、网关或登录态
- 当前验证目标是什么

### 2. 侦察

侦察时遵循：

- 打开页面后先等待稳定状态，例如 `networkidle`
- 先截图，再看渲染后的 DOM
- 先找可靠选择器，再执行动作
- 必要时记录控制台日志与关键报错

### 3. 动作

动作阶段优先做：

- 打开主页面
- 完成主查询、主提交或主点击链路
- 记录关键结果、提示语、错误信息

### 4. 验证

至少验证：

- 主链路是否通
- 页面是否报错
- 关键按钮、输入、表格、弹窗是否按预期变化
- 是否出现明显控制台错误

## Reconnaissance-Then-Action 模式

1. 打开页面并等待稳定
2. 截图或读取渲染后内容
3. 识别真实选择器
4. 再执行动作和断言

不要反过来：

- 不要在 JS 尚未渲染完成时就抓 DOM
- 不要凭猜测先写一长串选择器

## 适配规则

- 如果仓库已有 Playwright、E2E、helper 脚本，优先复用现有约定
- 如果需要先启动本地服务，优先调用现有启动命令或脚本
- 如果页面强依赖异步渲染，必须等待稳定状态再侦察 DOM
- 对已有后台系统，优先验证真实业务链路，不只检查样式是否渲染

## 最小验证清单

- 页面能打开
- 主链路能走通
- 无明显控制台错误
- 关键结果可观测
- 如有失败，能留下截图或日志

详细清单与最小脚本骨架见 `references/checklist.md`；真实黑盒闭环样例见 `references/closure_example.md`。

## 闭环门

- 验证前已明确页面、主链路、环境依赖和登录态边界。
- 验证后必须留下可观察证据：截图、控制台/网络摘要、断言结果或失败复现步骤。
- 黑盒证据不足以定位根因时，回到 `delivery-workflow` debug 路由，不在本技能内扩写实现方案。
- 若仓库已有 E2E/Playwright/helper 脚本，优先复用并记录命令结果。
- 收口前按 `references/behavior_audit.md` 反查只截图、漏 console/network、选择器猜测和可达性证据缺口。
