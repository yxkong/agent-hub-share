# 评分维度（双 100 分制）

## 总体输出

本技能默认输出三层结果：

1. **质量分（100）**：写得好不好
2. **兑现分（100）**：承诺能力有没有兑现
3. **门禁结论**：`可挂载 / 可复用 / 仅参考 / 暂缓使用`

## 质量分（100）

| 维度 | 分值 | 看什么 |
|------|------|--------|
| 边界与触发 | **15** | description 是否回答 WHAT + WHEN；正负触发是否准确 |
| 契约完整性 | **12** | 输入、输出、硬约束、前置条件是否清楚 |
| SOP 可执行性 | **15** | 是否能指导 AI 直接行动，而非空泛建议 |
| 资产结构 | **15** | README / SKILL / references / scripts / templates 分工是否清楚 |
| 可维护性 | **12** | 分层是否稳定、是否容易漂移、维护成本是否可控 |
| 生态适配 | **11** | 与相邻 skill、脚本分级、真源/镜像约定是否一致 |
| 首读效率 | **10** | Agent 触发后 30 秒内是否能判断先读哪份 active 文件 |
| 主文件纯度 | **10** | `SKILL.md` 是否只承载稳定入口/协议，不混入维护层、human-only、具体业务样例或长手册 |

合计：**100**

## 兑现分（100）

| 维度 | 分值 | 看什么 |
|------|------|--------|
| 路径与引用有效性 | **15** | 活跃路径、引用、真源/镜像、迁移后引用是否仍有效 |
| 脚本与入口可用性 | **15** | 脚本是否存在、能运行、wrapper 与正文是否一致 |
| 验证闭环 | **20** | 是否有验证方式、通过判据、失败收口 |
| 承诺能力覆盖 | **20** | skill/prompt 承诺的能力是否被真实内容与资产覆盖 |
| 行为有效性 | **15** | skill 是否真的改变 Agent 默认行为；高风险/纪律类是否有基线与复测证据 |
| 模板与派生资产同步 | **15** | prompt 模板、子 Agent 模板、示例、wrapper 是否仍跟当前规则同步 |

合计：**100**

## 证据等级

在打兑现分时，必须标证据等级：

| 等级 | 含义 |
|------|------|
| `executed` | 实际运行过脚本 / 校验 / 触发句 |
| `observed` | 有可靠运行结果、日志或客户端成功信号 |
| `static` | 仅做静态审计（读文件、看路径、看脚本） |
| `unknown` | 无法确认，不得伪装成已验证 |

默认规则：

- `executed` > `observed` > `static` > `unknown`
- 兑现分若主要基于 `static`，结论应更保守
- 若关键项为 `unknown`，门禁不得上升为 `可挂载`

## 门禁结论

门禁不由平均分直接得出，而由硬条件约束：

| 结论 | 典型条件 |
|------|----------|
| `可挂载` | 双分都高，且无关键阻断，兑现分有 `executed/observed` 支撑 |
| `可复用` | 质量高、兑现基本成立，但不一定适合直接挂载 |
| `仅参考` | 质量尚可，但兑现不足或证据偏静态 |
| `暂缓使用` | 关键路径失效、脚本不可用、承诺能力缺少兑现证据 |

## 兑现分封顶规则

满足任一条时，即使其他项较好，也应封顶：

| 情况 | 兑现分封顶 |
|------|------------|
| 没有验证方式，且无法证明主链路真的可执行 | **69** |
| 活跃路径 / 引用 / 脚本入口已失效 | **72** |
| share 资产仍硬编码真实项目名 / `platform-*` / 私有 URL | **72** |
| 脚本明显放错层，且正文 / README 没解释调用方式 | **74** |
| 只有理念和模板，没有契约、SOP、验证 | **59** |
| 只看了 `SKILL.md`，未盘点同目录 active 文件（排除 `bak/`）就给最终分 | **79** |
| 高风险 / 纪律类 skill 无法证明行为改变，只能静态说明“应该会遵守” | **76** |

## 质量分封顶规则

满足任一条时，质量分应封顶：

| 情况 | 质量分封顶 |
|------|------------|
| `SKILL.md` 是长手册，触发后必须通读大量正文才知道先做什么 | **82** |
| `SKILL.md` 混入 human-only / maintenance-only 文件枚举、具体业务样例或可变资产清单 | **85** |
| README / INDEX / 子目录 README 与 `SKILL.md` 形成并列入口 | **84** |

## 质量分常见扣分锚点

| 现象 | 质量分典型影响 |
|------|----------------|
| description 宽泛，触发不准 | 边界与触发降分 |
| SOP 像口号，不像动作 | SOP 可执行性降分 |
| README / SKILL / references 分工混乱 | 资产结构、可维护性降分 |
| 不负责 / 转交不清 | 边界与生态适配降分 |
| 触发后仍不知道先读哪份文件 | 首读效率降分 |
| 主文件承担了 references、README 或索引职责 | 主文件纯度降分 |

## 评分原则

1. **先判门禁大错，再做细分**
2. **有脚本但不可跑，比没有脚本更该扣兑现分**
3. **README 是维护章程，不是运行入口；其缺失或漂移主要扣质量分**
4. **share skill 的去项目化要求高于 project skill**
5. **vendor bundle** 既看单技能质量，也看整体一致性
6. **评分对象是整个 active 技能包**：必须盘点同目录 `SKILL.md`、`README.md`、`references/`、`scripts/`、`templates/` 等 active 文件；`bak/` 不计证据
7. **内容丰富不等于优秀 skill**：长手册型能力包可以兑现高，但若主入口不纯、首读成本高，质量分必须体现
